# TaskSystem — сервис управления заявками

Небольшое fullstack-приложение для учёта заявок сотрудников. Администратор создаёт заявки и назначает исполнителей, а сотрудники работают с назначенными им задачами. Проект реализован как тестовое задание; основное внимание уделено разграничению доступа, бизнес-правилам и корректной обработке одновременных изменений.

**Стек:** PHP 8.3+ / Laravel 12, React 19 / TypeScript, Vite, PostgreSQL 17, Docker Compose.

[Автоматические проверки проекта](https://github.com/andreygrigorasch/TaskSystem/actions/workflows/ci.yml)

## Возможности

- Вход и выход по серверной сессии; CSRF-защита и ограничение частоты попыток входа.
- Две роли: **администратор** (все заявки, создание и назначение) и **сотрудник** (только назначенные ему заявки).
- Просмотр списка и карточки заявки, фильтрация по статусу и серверная пагинация.
- Строгие переходы статусов: `new → in_progress → done`. Завершённая заявка недоступна для изменений.
- Контроль конкурентных изменений по полю `version`: при устаревшей версии API возвращает `409 Conflict`.
- Обработка загрузки, ошибок и конфликтов в интерфейсе.
- Миграции, демонстрационные данные и автоматические тесты.

## Быстрый запуск через Docker

**Нужно:** Docker с поддержкой Compose v2. Устанавливать PHP, Node.js и PostgreSQL на компьютер не требуется.

```bash
git clone https://github.com/andreygrigorasch/TaskSystem.git
cd TaskSystem
docker compose up --build
```

После запуска откройте **http://127.0.0.1:8000**.

При старте контейнер приложения выполняет миграции и заполнение демонстрационными данными. Сборка React входит в Dockerfile. Конфигурация БД для контейнеров уже задана в `compose.yaml`; создавать локальный `.env` для этого сценария не нужно.

Если порты `8000` или `5432` заняты:

```bash
APP_PORT=8080 DB_FORWARD_PORT=5433 docker compose up --build
```

В таком случае приложение будет доступно на **http://127.0.0.1:8080**.

Для остановки используйте `Ctrl+C` или выполните из другого терминала:

```bash
docker compose down
```

Данные PostgreSQL и ключ приложения сохраняются в Docker volumes. Команда `docker compose down -v` **удаляет volumes проекта вместе с данными**; используйте её только для полного сброса локального стенда.

## Локальный запуск без Docker

Потребуются PHP 8.3+ с расширениями PostgreSQL и стандартными расширениями Laravel, Composer 2, Node.js 22.12+, npm и PostgreSQL (рекомендуется 17).

**1. Получите код и установите зависимости:**

```bash
git clone https://github.com/andreygrigorasch/TaskSystem.git
cd TaskSystem
cp .env.example .env
cp .env.testing.example .env.testing
composer install
npm ci
```

**2. Создайте две отдельные базы данных.** Пример SQL для администратора PostgreSQL (если пользователь `app` ещё не существует):

```sql
CREATE ROLE app WITH LOGIN PASSWORD 'secret';
CREATE DATABASE request_desk OWNER app;
CREATE DATABASE request_desk_test OWNER app;
```

**3. До запуска миграций** проверьте параметры `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` и `DB_PASSWORD` в файлах `.env` и `.env.testing`. Основная база — `request_desk`, тестовая — **`request_desk_test`**. Пароль `secret` приведён только для локального примера; если используете другой, измените его в настройках подключения.

**4. Подготовьте и запустите приложение:**

```bash
php artisan key:generate
php artisan migrate --seed
npm run build
php artisan serve --host=127.0.0.1 --port=8000
```

Откройте **http://127.0.0.1:8000**.

Для разработки frontend вместо готовой сборки можно запустить в отдельном терминале `npm run dev`, оставив `php artisan serve` работающим. Если после завершения Vite приложение продолжает искать dev-сервер, удалите устаревший `public/hot` и выполните `npm run build`.

## Быстрая проверка в браузере

1. Войдите под `admin@example.com`, создайте заявку и назначьте исполнителя.
2. Войдите под `employee@example.com`: сотрудник должен видеть только свои заявки и не должен иметь возможности создавать новые.
3. Переведите доступную заявку из `new` в `in_progress`, затем в `done`. Попытка изменить завершённую заявку должна быть отклонена.
4. Откройте одну и ту же незавершённую заявку в двух вкладках. Измените её в первой вкладке, затем попробуйте сохранить устаревшее изменение во второй: интерфейс должен сообщить о конфликте и предложить загрузить актуальные данные.

## Основная бизнес-логика

1. Администратор может создать заявку без исполнителя и назначить сотрудника позднее. Сотрудник не может создавать заявки и видеть чужие.
2. Статус меняется только на следующий: `new → in_progress → done`. Пропуск, откат и повтор текущего статуса запрещены.
3. После перехода в `done` нельзя менять ни статус, ни исполнителя.
4. При создании заявки версия начинается с `1`; каждое успешное изменение статуса или исполнителя увеличивает `version`.
5. Запрос на изменение должен содержать версию, которую прочитал клиент. Если версия устарела, сервер возвращает `409 Conflict` без применения изменений.
6. Проверки прав и версии выполняются на сервере. Для изменения записи используется транзакция PostgreSQL и блокировка строки `SELECT … FOR UPDATE`.

## API

API и React-приложение работают на одном origin. Авторизация основана на cookie-сессии, а не на bearer-токенах. Для API-запросов используйте `Accept: application/json`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/csrf-cookie` | Получение CSRF-cookie |
| `POST` | `/api/login` | Вход (`email`, `password`) |
| `GET` | `/api/user` | Текущий пользователь |
| `POST` | `/api/logout` | Выход |
| `GET` | `/api/requests` | Список доступных заявок |
| `GET` | `/api/requests?status=new&page=1&per_page=10` | Фильтрация и пагинация |
| `GET` | `/api/requests/{id}` | Карточка заявки |
| `POST` | `/api/requests` | Создание (администратор) |
| `PATCH` | `/api/requests/{id}/status` | Изменение статуса |
| `PATCH` | `/api/requests/{id}/assignee` | Назначение исполнителя (администратор) |
| `GET` | `/api/employees` | Список исполнителей (администратор) |

**Пример изменения статуса:**

```http
PATCH /api/requests/1/status
Content-Type: application/json
Accept: application/json
```

```json
{
  "status": "in_progress",
  "version": 1
}
```

В ответе на успешное обновление будет актуальная версия заявки. Для изменения исполнителя отправьте `assignee_id` (ID сотрудника или `null`) и `version`.

Для POST/PATCH сначала получите cookie запросом `GET /api/csrf-cookie`, затем передавайте cookie сессии и заголовок `X-XSRF-TOKEN` со значением cookie `XSRF-TOKEN` после URL-декодирования. Это требуется и для входа через API.

Основные коды ошибок: `401` — нет сессии; `403` — недостаточно прав; `404` — запись не найдена; `409` — конфликт версии; `419` — ошибка CSRF; `422` — ошибка валидации или бизнес-правил; `429` — превышен лимит попыток входа.

## Тесты и проверки

**Внимание:** тесты используют отдельную базу `request_desk_test` и могут пересоздавать её таблицы. Не указывайте здесь рабочую базу данных. В `phpunit.xml` зафиксированы имя тестовой БД и отдельный публичный ключ шифрования только для тестов, а базовый `TestCase` дополнительно проверяет окружение и окончание имени БД на `_test`.

Локально (после настройки `.env.testing`):

```bash
composer test
npm run typecheck
npm run build
php vendor/bin/pint --test
composer validate --strict
```

В Docker при запущенных сервисах:

```bash
docker compose exec app composer test
```

Серверные тесты проверяют авторизацию и роли, доступ к заявкам, переходы статусов, валидацию, конфликты версий и конкурентные изменения в PostgreSQL. Проверка чистой копии: **21 тест, 138 assertions — успешно**. TypeScript, production-сборка и форматирование PHP также проходят. Актуальный результат доступен в выводе `composer test` и в GitHub Actions.

При push в `main` и в pull request GitHub Actions выполняет те же серверные проверки на PHP 8.3 / PostgreSQL 17, проверяет TypeScript и сборку frontend. Отдельная задача собирает Docker-образ из чистого checkout без `.env`, проверяет HTTP-ответ и выполняет тесты внутри контейнера. Обе задачи прошли [проверку на GitHub](https://github.com/andreygrigorasch/TaskSystem/actions/runs/42023666222). Проверки не публикуют приложение и не используют внешнюю рабочую базу данных.

## Структура проекта

```text
app/Enums/                      Роли и статусы
app/Models/                     Eloquent-модели
app/Policies/                   Проверка прав доступа
app/Actions/UpdateServiceRequest.php
                                Транзакции, блокировка и обновление версий
app/Http/Controllers/           API-контроллеры
app/Http/Resources/             Формат ответов API
routes/web.php                  API-маршруты и точка входа SPA
resources/js/                   React-приложение
resources/css/                  Стили
database/                       Миграции, фабрики, сидеры
tests/                          Автоматические тесты
docker/                         Файлы локального Docker-окружения
compose.yaml, Dockerfile        Конфигурация контейнеров
```

React собирается Vite в статические ресурсы; Laravel отдаёт и SPA, и API. Отдельный Node.js-сервер в рабочем режиме не нужен.

Контроллеры валидируют входные данные и формируют HTTP-ответы. Policies проверяют действия над отдельной записью, а область видимости модели ограничивает список. Единый Action выполняет изменения статуса и исполнителя: читает актуальную строку под `FOR UPDATE` внутри транзакции, повторно проверяет права, сравнивает версию, применяет бизнес-правила и увеличивает версию. Блокировка сохраняется до завершения транзакции; конкурирующий запрос после ожидания получает уже новую версию и возвращает 409. JSON Resource задаёт явный контракт ответа.

Принятые допущения: исполнитель может быть не назначен; назначать можно только сотрудников; администратор может менять статус неназначенной заявки. Название и описание задаются при создании. Отдельные repository-слои и глобальный frontend-store для текущего объёма не вводились.

## Ограничения

- Проект рассчитан на демонстрацию, а не на production-развёртывание. Docker использует `artisan serve`, тестовые пароли и HTTP без TLS.
- Не реализованы регистрация, удаление заявок, редактирование названия и описания после создания, уведомления и журнал действий — они не входят в объём тестового задания.
- Конфликты изменений не разрешаются автоматически: пользователь должен обновить заявку и повторить действие с актуальной версией.
- Основная реализация ориентирована на PostgreSQL; совместимость с MySQL не подтверждена.

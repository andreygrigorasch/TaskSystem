# Сервис управления заявками

Тестовое задание из `testovoe_zadanie_fullstack_razrabotchik.pdf`. Laravel 12, PHP 8.3+, React 19, TypeScript, PostgreSQL 17.

## Что реализовано

- Авторизация через серверную сессию, выход, CSRF-защита и ограничение частоты входа. Регистрации нет.
- Администратор видит все заявки, создаёт их, назначает и меняет исполнителя, переводит заявку в следующий статус.
- Сотрудник видит только назначенные ему заявки и меняет их статус. Ограничения проверяются сервером, включая прямые обращения к API.
- Последовательность `new → in_progress → done`. Пропуск, обратный переход и повтор текущего статуса отклоняются. В `done` запрещены любые доступные операции изменения, включая переназначение.
- Каждая запись содержит название, описание, статус, исполнителя, даты создания/изменения и `version`, начиная с 1.
- Все изменения требуют `version`. Устаревшая версия даёт `409 Conflict`, без перезаписи данных.
- Список, фильтр по статусу, серверная пагинация, детали, создание и назначение в интерфейсе. Фильтр и страница сохраняются в URL, ссылка на заявку открывается напрямую.
- Отображение загрузки, ошибок, пустого списка, успешного сохранения и конфликта. После 409 необходимо явно загрузить актуальную заявку; автоматически повторять изменение интерфейс не будет.
- Миграции, идемпотентные сидеры с 3 пользователями и 12 примерами, PHPUnit-тесты.

## Быстрый запуск в Docker

Требования: Docker с Compose v2.

```sh
git clone https://github.com/andreygrigorasch/TaskSystem.git
cd TaskSystem
cp .env.example .env
docker compose up --build
```

Откройте **http://127.0.0.1:8000**. На первом запуске автоматически создаются схема и тестовые данные. Frontend собирается внутри Docker. Composer-зависимости закреплены под PHP 8.3, версии npm — в lock-файле.

Если стандартные порты заняты:

```sh
APP_PORT=8080 DB_FORWARD_PORT=5433 docker compose up --build
```

Данные PostgreSQL и ключ сессии сохраняются в именованных volumes. При пустом `APP_KEY` контейнер создаёт случайный ключ и сохраняет его в `storage/app/.app-key`; заданный вами `APP_KEY` имеет приоритет.

```sh
docker compose down
```

Команда останавливает сервисы, сохраняя данные. Для полного удаления **только демонстрационных данных этого проекта**: `docker compose down -v`.

## Запуск без Docker

Нужны PHP 8.3+ с `pdo_pgsql`, `mbstring`, `openssl`, `xml`, `dom`, `xmlwriter`, `tokenizer`, `ctype`, `fileinfo`; Composer 2; Node.js 22.12+; npm; PostgreSQL 15+.

Создайте пользователя и две отдельные базы. Например, через `psql` от администратора PostgreSQL:

```sql
CREATE ROLE app WITH LOGIN PASSWORD 'secret';
CREATE DATABASE request_desk OWNER app;
CREATE DATABASE request_desk_test OWNER app;
```

```sh
cp .env.example .env
cp .env.testing.example .env.testing
composer install
php artisan key:generate
npm ci
npm run build
php artisan migrate --seed
php artisan serve --host=127.0.0.1 --port=8000
```

Настройте `DB_HOST`, `DB_PORT`, `DB_USERNAME`, `DB_PASSWORD` в `.env` и `.env.testing` под ваш PostgreSQL. `.env.testing` должна указывать на отдельную тестовую БД. Ключ из `.env.testing.example` публичный и предназначен только для тестов; для приложения `key:generate` создаёт отдельный ключ.

Для разработки оставьте Laravel-сервер работающим и в другом терминале выполните `npm run dev`. При переходе обратно к готовой сборке остановите Vite и удалите `public/hot`, если он остался после аварийного завершения.

PHPUnit принудительно использует `APP_ENV=testing`, `DB_CONNECTION=pgsql` и БД `request_desk_test`. Для безопасности базовый TestCase отказывается работать, если имя БД не заканчивается на `_test`, до запуска миграций. Набор тестов пересоздаёт **тестовую** схему. Основная БД не используется.

21 тест покрывает:

- вход, неверные данные, выход, ограничение частоты входа;
- доступ сотрудника только к своим данным, защиту операций создания/назначения;
- серверные фильтр и пагинацию без утечки чужих заявок;
- допустимую последовательность, запрещённые пропуски/повторы/обратные переходы;
- неизменяемость завершённой заявки для администратора;
- 401/403/404/409/422, обязательную версию и валидацию исполнителя;
- увеличение версии при переназначении и немедленную потерю доступа прежним исполнителем;
- защиту от изменения посторонних полей через endpoint статуса;
- **реальную конкуренцию двух независимых PHP-процессов на PostgreSQL**: одновременные смена статуса и назначение с одной версией дают один успех и один 409.

В тесте конкуренции родитель удерживает блокировку строки до готовности двух процессов, затем освобождает её. Оба пытаются записать изменения с версией 1. В результате версия становится 2 и сохраняется ровно одна операция. Проверка выполняется на PostgreSQL, без SQLite и имитации блокировок.

Проверенная локальная среда: PHP 8.4.5, PostgreSQL 17.11, Node.js 22.23.2.

Результат проверки: **21 тест, 138 assertions — успешно**. TypeScript, production-сборка Vite, Pint и валидация Composer также прошли.

Через Chromium проверены вход, создание и переназначение, фильтр, пагинация, загрузка, ошибка API и повторная попытка, пустая страница, порядок клавиатурного фокуса и ширины 320/375/768/1024/1440 px. В двух вкладках воспроизведён настоящий 409, блокировка повторного действия и восстановление после обновления. Назначенный сотрудник завершил заявку; чужая заявка вернула 403, завершённая стала недоступна для изменений. Ошибок JavaScript при прохождении сценариев не обнаружено; ожидаемые HTTP 401/403/409 и тестовый 500 проверялись отдельно.

Laravel отключает CSRF middleware в PHPUnit; фактическая cookie/CSRF-авторизация дополнительно проверена через настоящий HTTP-сервер. Запрос без CSRF-токена вернул 419, с корректным CSRF без авторизации — 401. Скриншоты локальных проверок не включены в репозиторий.

## API

Все адреса относительные, API и SPA обслуживаются с одного origin. Ответы API — JSON; отправляйте `Accept: application/json`.

Для входа сначала выполните `GET /api/csrf-cookie`, сохраните cookie. На POST/PATCH отправляйте cookie сессии и заголовок `X-XSRF-TOKEN` с URL-декодированным значением cookie `XSRF-TOKEN`. Cookie сессии HttpOnly; токены авторизации в localStorage не используются. CSRF не исключён ни для одного API-маршрута.

| Метод | URL | Доступ / тело |
| --- | --- | --- |
| GET | `/api/csrf-cookie` | Всем, инициализирует CSRF-cookie, 204 |
| POST | `/api/login` | `{ "email": "…", "password": "…" }` |
| GET | `/api/user` | Авторизованным, текущий пользователь |
| POST | `/api/logout` | Авторизованным, 204 |
| GET | `/api/requests` | Доступные текущему пользователю заявки |
| GET | `/api/requests?status=new&page=1&per_page=10` | Фильтр и пагинация, `per_page` 1–100 |
| GET | `/api/requests/{id}` | Администратор или назначенный сотрудник |
| POST | `/api/requests` | Администратор; `title`, `description`, необязательный `assignee_id` |
| PATCH | `/api/requests/{id}/status` | Администратор/исполнитель; `status`, `version` |
| PATCH | `/api/requests/{id}/assignee` | Администратор; `assignee_id` (или `null`), `version` |
| GET | `/api/employees` | Администратор; список сотрудников для назначения |

Пример изменения:

```json
{ "status": "in_progress", "version": 1 }
```

Ответ `200` содержит `{ "data": { …, "status": "in_progress", "version": 2 } }`. Создание возвращает `201`; список — `data`, `links`, `meta`. Даты в API — ISO 8601 UTC, в интерфейсе — местное время браузера.

Ошибки:

| Код | Значение |
| --- | --- |
| 401 | Нет действительной сессии |
| 403 | Чужая заявка или действие, недоступное роли |
| 404 | Нет такой заявки или API-маршрута |
| 409 | Устаревшая версия; `code: version_conflict` |
| 419 | Нет корректного CSRF-токена; обновить сессию |
| 422 | Ошибки полей или бизнес-правил, `errors` по полям |
| 429 | Слишком много запросов входа |

Порядок проверки изменения: авторизация → входные данные → повторная авторизация по заблокированной строке → версия → завершённость → допустимость перехода → запись. Поэтому устаревшая версия завершённой заявки даёт 409, актуальная попытка изменения `done` — 422. Запрос без сессии и CSRF-токена может получить 419 до проверки авторизации; при корректном CSRF-токене без сессии — 401.

## Архитектура

Это один Laravel-проект с React SPA в `resources/js`, без отдельного Node-сервера. Vite собирает статические assets, Laravel отдаёт HTML и REST API. Такой вариант не требует CORS, отдельных доменов и хранения bearer-токенов на клиенте.

```text
app/Enums/                    роли и последовательность статусов
app/Models/                   Eloquent-модели и область видимости списка
app/Policies/                 серверные права доступа
app/Actions/UpdateServiceRequest.php
                              транзакция, блокировка, версия, бизнес-правила
app/Http/Controllers/         валидация и HTTP-операции
app/Http/Resources/            явный контракт JSON
app/Exceptions/               HTTP 409
routes/web.php                API с session/CSRF middleware и входная точка SPA
database/                     миграции, фабрики, сидеры
resources/js/pages/           вход, список, создание, детали
resources/js/api.ts            HTTP-клиент и CSRF
resources/js/useApiQuery.ts    загрузка с отменой устаревших запросов
resources/css/app.css         адаптивные стили и общие CSS-токены
tests/Feature/                API и конкурентная запись
tests/Support/                отдельный процесс для теста конкуренции
docker/                       локальное окружение
```

**Конкурентная запись.** Клиент передаёт прочитанную версию, сервер внутри короткой транзакции получает актуальную строку через `SELECT … FOR UPDATE`. После ожидания блокировки второй запрос видит уже увеличенную версию и возвращает 409. Проверка версии не отделена от записи, поэтому два запроса не могут оба пройти её на старом состоянии. Права также повторно проверяются после блокировки, чтобы сотрудник не успел изменить уже переназначенную заявку. Одинаковый механизм используется для статуса и исполнителя.

**Принятые решения.** Заявка может быть без исполнителя; её видит только администратор. Исполнителем может быть только сотрудник. Название и описание после создания не редактируются: такая операция не требовалась в PDF. Администратор может продвигать и неназначенную заявку; дополнительного ограничения в задании нет. Валидация остаётся в небольших контроллерах, правила изменения вынесены в один Action; дополнительные слои repository/service для двух моделей не вводились.

## Ограничения

- Реализован PostgreSQL; MySQL не проверялся. SQLite не используется для проверки блокировок.
- Docker-сценарий предназначен для локальной демонстрации: используется `artisan serve`, тестовые пароли и нет HTTPS. Для production нужны reverse proxy/PHP-FPM, HTTPS, secure cookies, секреты и отдельный процесс выпуска миграций.
- Нет регистрации, редактирования текста заявки, удаления, уведомлений, realtime-подписок и журнала действий: это за пределами задания. Актуализация — по кнопке или после собственного изменения.
- Конфликт не объединяет изменения автоматически: пользователь читает актуальную заявку и повторяет действие осознанно.
- Браузерная и серверная проверка выполнены на локальной установке. Docker CLI в среде выполнения отсутствует; Dockerfile и Compose подготовлены, но сборка контейнера здесь не запускалась.
